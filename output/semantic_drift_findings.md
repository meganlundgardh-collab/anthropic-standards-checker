Stage B — the actual semantic comparison — needs a live model call; this sandbox has network access to `api.anthropic.com` but no `ANTHROPIC_API_KEY` configured, so the script correctly stopped rather than faking a result.

What follows is Stage B run by hand: each prompt below is copied verbatim from `semantic_drift_candidates.json`'s `stage_b_prompt` field, and each verdict is what applying that exact prompt produced. This is the honest state of this module — a real Anthropic-API integration (see `call_model()` in the script) that would run unattended with a key, executed manually this one time because no key exists in the build environment. Labeling it this way instead of quietly hand-writing "sample output" is the same principle the rest of this submission follows: say what actually ran.

## What this run actually demonstrates

**The headline result (#6) is the one the module was built to test, and it passed.** Without the DISTINCT_CONCEPT category, this checker would have flagged Claude Tag's "connection" definition as drift against the canonical connector definition — exactly the false conclusion a human would have to catch by hand, the same way the Part 2 stress test caught it in the first place. Building DISTINCT_CONCEPT in as a first-class verdict, not an afterthought, is what let the checker get this one right instead of needing a human override.

**But #7, on the same page, one section later, is real drift** — a genuine, previously-undocumented instance of Rule 1's pattern that neither Part 1's original audit nor the Part 2 stress test surfaced, because neither was looking at plugin *definitions* specifically. It's a nice demonstration that "this page correctly handles the hard case" and "this page is otherwise clean" are independent facts.

**#2 and #3 (the "hooks" drift on the Government plugins page) are the most concrete new finding this module produced.** Hooks aren't in canonical `plugins/overview.md` anywhere — confirmed by grepping the full scraped page, not just the opening summary — so a Government-surface reader would learn about a plugin capability (local hook execution) that the canonical source of truth doesn't document at all. This overlaps with, but isn't identical to, Part 1 finding #5 ("four pages, four different plugin component lists"): finding #5 was about component *tables*; this is the same drift pattern showing up in defining *prose*, which is specifically the surface Rule 1 (not Rule 2) exists to catch. Worth flagging in Part 1/Part 2 follow-up as a live example, not just a hypothetical one.

**#5 is the most instructive result of the run, and it isn't primarily a Rule 1 finding at all.** `government/desktop/skills.md` is independently re-derived as a live instance of finding #6 (Rule 1's own origin story) and a clear Rule 5(b) violation — a Tier 3 surface page carrying a full skill-authoring/build walkthrough that duplicates `skills/how-to.md`. See "What changed in this rerun," below, for how the checker went from needing a human to reread the whole page to catch this, to surfacing it directly in Stage B's own output.

**#9 is the second-most instructive, and it's a confirmation, not a new problem.** Two independent Claude Tag pages (`add-connections.md` for #6, `customize.md` for #9) each carry their own, differently-worded disclaimer that "connection" (channel/admin-scoped) isn't "connector" (personal). Finding the same correct disambiguation twice, from two different authors' worth of prose, is better evidence that this is a deliberate site convention than either instance is alone — and it only surfaced because Stage A's extraction pattern was widened, see below.

## What changed in this rerun

The first pass's `PROMPT_TEMPLATE` handed Stage B only the matched sentence and the canonical definition — nothing about where on the page that sentence sat. That was enough to get Rule 1's own narrow question right in every case, but candidate #5 showed it wasn't enough to catch a *different* rule's violation hiding one level up: the isolated sentence reads as harmless, and only the section it opens reveals the problem.

The fix, in `find_definition_candidates_with_context()`: Stage A now walks each page section by section (splitting on H2s) and records, for every definitional sentence it finds, which section it's under, that section's total sentence count, and the full paragraph the sentence belongs to. `PROMPT_TEMPLATE` now includes all three, and explicitly asks Stage B to flag a Rule 5 concern from that context even when it doesn't change the Rule 1 verdict on the sentence itself.

Rerunning Stage A produced the same 8 candidates (the extraction logic that finds *candidates* didn't change, only what context ships with each one) — worth confirming, since a script that quietly finds different candidates after a fix is a script you can't trust the diff on. Reapplying Stage B by hand with the new prompts produced the **same verdict on every one of the 8** — including the two Claude Tag sections that turned out to be large (24 and 26 sentences: "Your first Access bundle" and "Attach plugins") but are legitimate admin-instruction content, not authoring/build duplication, so correctly raised no Rule 5 concern (Claude Tag isn't governed by the Tier 3 template in the first place — Part 2's stress test already established that). The one thing that changed is *how* candidate #5's Rule 5 problem got caught: previously it took a human rereading the whole page after Stage B's verdict came back too clean; now Stage B's own output states it directly, in the same pass, because it was handed the same context a human reviewer would have used.

## What changed in the third pass (widening DEFINITION_RE)

`DEFINITION_RE` originally required a literal article — `a`/`an` — directly before the primitive noun (`\b[Aa]n?\s+(plugin|skill|connector|connection)s?\s+(?:is|are|...)`). A hand sweep of all 9 surface pages for near-miss phrases (`<word> (plugin|skill|connector|connection)s? (is|are|...)`) found this was mostly the right call — "uploaded plugins are not controlled by Anthropic," "This plugin is required by your organization," and "the options to create and upload skills are hidden" are all correctly *not* definitions (a trust caveat, a UI label, a UI-state description), and the article requirement correctly excludes them. But one real miss turned up: `claude-tag/admins/customize.md` has an H3 section titled "### Channel connections are separate from personal connectors" — a genuine, on-topic distinction between the canonical `connector` and Claude Tag's `connection`, invisible to Stage A only because "Channel" sits where "a"/"an" would need to be.

**The fix, deliberately narrow:** added a second alternative to `DEFINITION_RE` that matches a capitalized single-word modifier + plural primitive + "are", anchored to the *start* of the sentence (`^[A-Z][a-z]+\s+(plugin|skill|connector|connection)s\s+are\b`). Both restrictions were load-bearing, not arbitrary: restricting to plural "are" (not singular "is") is what keeps out "Each connection is listed in the bundle..." and "This plugin is required..." — both singular, both false leads, both share the same shape otherwise. Anchoring to sentence-start is what keeps out "...since uploaded plugins are not controlled by Anthropic" and "...the options to create and upload skills are hidden" — both real sentences containing the trigger words, but not at the start of their sentence, because they're subordinate clauses inside a larger sentence about something else.

**A second, smaller bug had to be fixed alongside it to make the new branch usable at all.** `find_definition_candidates_with_context()` only strips heading markup for H1 (before extraction starts) and H2 (splits sections but discards the "## "). An H3+ heading like "### Channel connections are separate from personal connectors" was left with its literal "###" in the text handed to the sentence splitter — which, since it's followed by a blank line, becomes its own paragraph whose text *starts with* "###", breaking the new branch's `^[A-Z]` anchor before it could ever match. Fixed by stripping any `#{3,6}\s+` prefix when building each section's body text, so a sub-heading reads as plain prose everywhere downstream (sentence-splitting, the Stage B prompt's paragraph-context field) the same as it would if it were an ordinary sentence.

**Result: 10 candidates, up from 8 (verified via diff against the pre-widening `semantic_drift_candidates.json` — the original 8 candidates' text, section heading, paragraph context, and full Stage B prompt are byte-for-byte unchanged).** Both new candidates are verdicts #9 and #10, above. One page (`claude-science/enable-claude-science.md`) moved from correctly-abstained (`NO_LOCAL_DEFINITION`) to producing a real candidate; the other 8 pages' candidate counts didn't change.

**Disclosed, not fixed: the widening still misses one more near-hit, and it's not the regex's fault this time.** The same paragraph that produced candidate #10 also contains "Directory connectors are additional life sciences connectors from the Claude connector directory." — a sentence that should match the new branch (`Directory` + `connectors` + `are`) but doesn't, because the source markdown uses a trailing `\` for a manual line break: `"...off in the app.\\\nDirectory connectors are..."`. `split_sentences()` collapses the newline but leaves the literal backslash character, and the sentence-boundary regex (`(?<=[.!?])\s+`) requires whitespace immediately after a period — the backslash sits in between, so no split happens there, and "Directory connectors are..." ends up merged mid-string into the *previous* sentence instead of starting its own, where the new branch's `^` anchor can't reach it. Confirmed by reproducing the exact `split_sentences()` output on this paragraph in isolation. Left as a known limitation rather than patched further in this pass — a general fix (stripping or normalizing trailing markdown line-continuation backslashes before sentence-splitting) is a reasonable next step but is a different kind of bug from the one this pass set out to fix, and deserves its own look rather than a rushed addition here.

## Known limitations, disclosed rather than patched

- **Stage A's length heuristic is currently too blunt to trust on its own.** It counts every sentence in the opening block (H1 to first H2), not just sentences that are part of the definitional claim — so it flagged all 10 of 10 candidates (across all 6 pages that produced any) as "possible canonical substitute," including `/cowork/guide/plugins`, which is CONSISTENT and is Rule 1's own template-correct example. A useful version would scope the count to the sentence(s) actually forming the local definition, not the whole opening block (which often includes availability notes, admonitions, and other non-definitional prose). Left un-fixed here on purpose, same reasoning as `link_checker.py`'s stemming gap: documenting a known-bad heuristic is more useful than quietly narrowing this run's sample until it looks clean. (Note: this heuristic is separate from the new per-section `section_sentence_count` field, which turned out to be exactly the useful version of this idea, just scoped to the section containing the actual definition rather than the page's whole opening block.)
- **Stage A found this run's most important candidate only after a real bug fix, mid-build.** The first version of `extract_full_body()` only scanned the opening block (H1 to first H2) for definitional sentences, which missed `claude-tag/admins/add-connections.md`'s "connection" definition entirely, because it lives under that page's first H2, not before it. Widened to scan the whole page body. Left as a code comment in the script rather than silently fixed, since it's a real example of exactly the class of checker mistake this whole project has been surfacing and correcting in the open.
- **Stage B ran manually, not via the API, for this submission.** The integration code is real and would run unattended with `ANTHROPIC_API_KEY` set; see `checker/semantic_drift_checker.py`'s `call_model()`. What's in this file is that same prompt applied by a person (me) reading the same text a model would, once, without the retry/consistency-checking that a production version would need — see the README's "evaluating the checker" section for why a single judgment call (model or human) shouldn't be trusted uncritically for exactly the reason this whole project's Part 1 correction saga demonstrated.
- **The Rule 5 signal Stage B produces is still just a flag in the rationale text, not a structured, separately-actionable verdict.** It rides along inside the Rule 1 response rather than being its own classification with its own severity/counts. A more complete version would give Rule 5 its own verdict field (or its own checker pass entirely) rather than asking one prompt to opportunistically catch a second rule's violations as a side effect.
